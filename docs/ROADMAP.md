# Roadmap

This file is the plan of alerts. The Status page of the site reads it, and the tracker of the project mirrors it.

The goal of phase 1: the system does not miss a life-safety warning at a watched place. Each kind of input has two or more independent sources. The delivery repeats until the person acknowledges. A watchdog and an outside heartbeat watch the system.

The repo is public. It holds the general framework only. People, places, keys and the choices of the owner stay in a private configuration.

| AL-8 | Weather and emergency sources | in progress | The NWS API, IEM and FEMA IPAWS, each a procedure package with recorded fixtures. The CAP feed of the NWS comes from the service of the NWS API, so it is not an independent source. The NWS API source is done. Its fetch sends conditional requests. The package `format-nws` holds the VTEC code and the kinds of the NWS and SAME event codes. The package `format-cap` reads CAP 1.2 messages. The core finds a source that is late against another source. The IPAWS source is done: it carries a copy of each WEA message of the NWS, and the expectation `nws-api.ipaws` examines it. The NWS API source asks for each WEA message of the country, so the expectation has the two sides. The package `fetch` holds the request and the map of failures that the sources share. The IEM source is done: the Iowa Environmental Mesonet lists the NWS events in effect, from its own feeds of the NWS products. The IEM list is a snapshot, so the runtime ends a row that is absent from two complete lists in a row. The count two is a shortcut. A measure in CI compares the IEM list to the NWS API four times each day. The function `missesDecision` gives the count from it: the smallest count whose false ends are 1 in 100 or fewer of the true ends. A late source does not teach its limit: a check has its deadline at its start, and a missed check enters the sample at the limit (PR #121). |
| AL-9 | Pushover delivery with acknowledge and escalate | done | Emergency priority with iOS Critical Alerts, tested on the phone of the owner. The core reads the receipt and escalates to the next step. The quiet window of a person is done, on `inWindow` of `@mark1russell7/algebra/clock` 0.8.7. The Pushover channel package is done. The delivery step of AL-11 sends through it, and a key with a bad form stops the start of the instance. A late send stays in flight, and the channel cancels by the tag of the delivery key. |
| AL-10 | Source health and coverage | done | A health state machine for each source, and the count of independent failure domains of each kind at each place. A source that is down and a gap of the coverage are system reports in the same pipeline. |
| AL-11 | Operate as a service | done | The service runner of `@mark1russell7/service`, with an append-only event log in SQLite. The event log, the fold of each event and the view of the system at a time are done. A restart rebuilds each fold from the log. The delivery step is done: the route of each incident, the sends, the polls of the receipts and the cancels. The service loop, the status API, the liveness check, the instance of the owner and the entry are done. The host is done: a boot task, a supervisor that starts the runtime again, and a staged stop. The instance operates on the computer of the owner, with the private configuration (2026-11-15). |
| AL-12 | Outside heartbeat | done | The running system pings Healthchecks.io after each pass with no error, and pings `/fail` when a channel refuses a send. When the pings stop, Healthchecks.io alerts the owner. The live instance pings its check (2026-11-15). |
| AL-13 | Fault tests of the pipeline | blocked | Fault plans from rigor: a source down, slow, duplicated, out of order or with a changed format, a channel down, a copy stopped, a hard stop of the runtime in a delivery, a step of the wall clock, a lock or a broken file of the log. A gate holds each case. |
| AL-37 | The call rules of each channel | done | A channel declares the most calls in progress at the same time. Pushover sets 2. The stop probe of a down channel backs off, up to 60 seconds. Fault case 7 measured 12 failed probes in a 10 minute outage, not 175. |
| AL-42 | A cap and a balance watch for each paid service | in progress | A paid channel has a monthly cap of its spend in cents, on the quota gate of `polite-crawler`. The runtime reads the balance of each account each day. A low balance, an empty balance or a balance with no read is a line of system reports. The private configuration holds the cap, the reserve and the floor of each account (`spend`). The instance gives the cap and the balance watch to the Twilio call channel (AL-15). The core is live since 2026-11-16. Next: the spend entry of Twilio in the private configuration, after the answer of the owner on the cap. |
| AL-38 | The end of an alert when the threat leaves a place | blocked | When a live incident no longer reaches a person, the escalation of the person ends, and the repeats stop. The log keeps that end. When the threat comes back, a new escalation starts with new message keys. An acknowledgment before the end does not stop the new escalation. The code is done (#124). It waits for two gates: the partial-cancel arm and the come-back arm of fault case 9, and an incident that drops the codes that a later copy does not name. |
| AL-39 | A fetch stops at its time limit | done | Each fetch gets a signal. The runtime aborts it at the time limit and at the stop of the runtime. Thus no request waits behind the park of its host and goes later. Fault case 8 found 6 IPAWS fetches in 6 seconds after an outage. A fetch that fails after the stop writes nothing, and the next pass fetches the source again. |
| AL-45 | A source that comes due during a pass | done | A source that comes due while the fetches of a pass run wakes the next pass at once. Before, the loop took it for a fault and waited its retry. |
| AL-48 | A restart of the live runtime with no elevated shell | done | A new text of the restart request restarts the runtime. `install.ts restart` checks the files with the new code, writes the request and waits for the ready runtime. Live since 2026-11-16: each deploy uses it. |
| AL-49 | The runtime follows a step of the wall clock | in progress | A correction of the system time moves the wall clock. The runtime writes each step to its log and moves its own times by it. Thus each timer keeps its time, and the times of the sources do not move. A system report tells the step in the digest. Fault case 11 holds it. |
| AL-44 | The outage call | in progress | When the instance is down, the outside check starts three Functions on the server of Twilio. They call each person in the order of the list, until the person presses 1. A voicemail does not count. The private configuration holds the list (`outage`). The worker `outage` of the runtime deploys the Functions and the list at each start and once in each day. Next: the webhook of the outside check and a drill. |
| AL-50 | A broken log file at the boot | in progress | At the boot, the runtime checks its log file. A broken file goes into a quarantine folder, and a new file gets each event that the salvage reads. A system report names the folder. A loss of events gets `notice`, and a whole salvage gets `digest`. Fault case 12 tests it. |
| AL-29 | A standalone weather radio | waiting | The owner sets up a SAME weather radio at the bed. It needs no internet and no part of this system. |
| AL-30 | NWWS-OI, the push feed of the NWS | waiting | Each NWS product in CAP within 10 seconds, over XMPP, from servers apart from the NWS API. It is the second path for NWS warnings. The owner asks the NWS for two accounts. |

## Phase 2: wider and harder

| ID | Item | Status | Summary |
| --- | --- | --- | --- |
| AL-14 | More hazards | in progress | Earthquakes, floods, hurricanes, air quality, wildfire smoke, space weather and power outages, each with two or more sources. The first is the USGS earthquake feed: the package `source-usgs`. The package `quake` gives a disc for each band of the shaking, from the laws of Atkinson and Wald (2007). The package `source-emsc` reads the event service of EMSC, a second path, and round 4 of the atlas adopts it. The runtime reads the USGS and EMSC each minute. Rule 3 of the merge joins the reports of one earthquake from two sources: 30 s, 100 km and 1.0 of magnitude (`link.ts`). For US events, EMSC relays the solutions of the US networks, so it is not a second origin there. The package `source-tsunami` reads the latest CAP file of each tsunami warning center of the NWS, and round 5 of the atlas adopts it. A bulletin puts a warning, an advisory and a watch in the info blocks of one CAP message. So `capReports` of `format-cap` gives one report for each block, for IPAWS and the centers. The runtime does not read the centers yet. |
| AL-15 | Text and voice | in progress | Text messages and voice calls as the next step of the escalation, on a second provider. A second Healthchecks.io check is done in the code (#110): when the pings stop, its Twilio integration telephones the owner. The Twilio client is in `@procedures/notify`. The Twilio call channel is done in the code: the call, its state, its end and the cap of the spend. The instance makes the channel from the keys of Twilio, with the cap and the balance watch of the spend entry. The channel is live since 2026-11-16. Next: the steps of the calls in the private configuration. |
| AL-16 | A cloud copy | in progress | A second copy of the system on a cloud server. The copies exchange their ledgers, and the copy with rank 0 sends first. `CONTRACTS.md` has the design. The settings of a copy, the rank wait and the import of the pages of another copy are in the code. Next: the transport of the exchange, the host on Linux and the shared cap. The server waits for the owner. |
| AL-17 | People and places from the private store | in progress | The system reads people and places from the private configuration at run time. The format `AlertConfig`, its schema and its load are done in the core. The loader of the runtime is done: the entry reads the private folder through it. The start keeps the last good copy, and a valid change restarts the runtime. The runtime adds the codes of the zones near each place from the outlines. Thus a writer gives a position and the code of the county. Next: the private store of the owner writes the file with the steps of the check. |
| AL-18 | A UI with a map and overlays | in progress | Live incidents, warning areas, places and coverage on a map, with a view by criticality. The view of the map (`mapView` of the core), the renderer with no outside tiles, the local page, the store of zone shapes (`alerts-shapes-nws`) and the store in the runtime are done. The route `GET /map` of the runtime gives the map of the last pass. Next: the runtime serves the local page, and the demo on the new renderer. |
| AL-33 | Fire weather zones as a region system | later | An NWS fire zone and a forecast zone can have the same code and different outlines. Today each zone code is a forecast zone. A region system for fire zones goes into the match, the store of shapes and the map. |
| AL-19 | Technical outages and news | blocked | Status pages, cloud regions, internet outages and breaking news, with the same merge and priority. News has three uses, in this order: a second witness for an official warning, breaking events near the watched places, and a daily digest. This item fetches the feeds, and AL-34 reads them. |
| AL-34 | A news reader with a ladder of models | later | Free rules and sentiment scores read each news item first. A small model reads the items that they flag, and a larger model reads only the hard cases. The reader gives each item a kind, a place and a probability. Thus news goes into the same merge as the official warnings. Before the reader ships, a test on the same items compares the ladder with one model at low effort. |
| AL-35 | Relevance from an interest graph | in progress | An event has subjects: places at each scale, topics and entities. Each person has a graph of interests, with a weight, an opt-in or an opt-out for each subject. A path of dependencies joins an entity to a person. The relevance is a function of these paths. It is the factor of AL-31 for the person, and each alert tells why it came. Each default shows as a row that the person can see and change. Step 1, the study, is done (2026-11-15). Step 2 is the types, their schemas and `docs/RELEVANCE.md`. Step 3 is the exact calculation in `@mark1russell7/collections`. Step 4 is the relevance in the core, with its gates. Step 5 is the routing by the relevance: the core first, then the runtime configuration. |
| AL-36 | The source atlas | in progress | Each class of signal and each candidate source, as data in `packages/atlas`: the access, the terms, the cost, the delay, the coverage and the decision with its reason. The id of each class is a code of the core taxonomy. A gate holds two or more sources with no risk for each class, or a reason for fewer. The cover of each class has layers: the adopted sources, the distinct paths and the distinct origins. A parent class counts them at one leaf code. An origin can hold only in a region, so the origin layer counts the part of the Earth with the fewest origins. Round 1 has 200 classes and 181 sources, with prediction markets. Round 3 plans ODIN, a free public API of the active power outages by county. It also adds the region of the United States, where the origin of EMSC is USGS. Research rounds each week find more classes. |
| AL-25 | Radio input through an SDR | blocked | A software-defined radio receives NOAA Weather Radio, and the system decodes its SAME headers. This input needs no internet. |

| AL-20 | Preparedness planner | later | Hazard likelihood times exposure gives what to buy and do first, and an action plan for each hazard and each person. |
| AL-31 | Priority from probabilities and costs | in progress | The level becomes the expected harm against the cost to interrupt the person. Data gives each factor, not a guess. Step 1: measures in CI. The IEM verification records give the share of NWS warnings that verify, for each type. The NCEI storm records give the deaths and injuries of each event type. CAP 1.2 gives the probability of each certainty word. Step 2: the core calculates the score in shadow, next to the table. The table decides each send, and a gate holds this. The core has the factors, the expected harm and the gate. The map from the measures of step 1 to the priors is next. Step 3: the view and the live log show each difference. Step 4: the owner sets the risk that wakes a person at night. Then the score decides above the table, and the table stays the floor of the life-safety kinds. |
